## Application evidence and trace

The latest row in
[`copilot-usage.csv`](../../../.lattice-data/copilot-usage.csv) is timestamped
`2026-11-02T08:52:03.810Z` and records deployment `gpt-4o-mini`, API version
`2025-01-01-preview`, attempt `1`, HTTP status `401`, and outcome
`provider-http-error`. Because a row was written, this failure was not replaced
by the previous `usage-ledger-error`.

The application path is:

1. `completeCopilotTurn()` receives the provider HTTP response and writes the
   usage record before throwing. The current record proves this write
   succeeded.
2. For a non-2xx response, the Azure client throws
   `AzureOpenAIError("provider-http-error", "Azure OpenAI request failed with status 401.", 401)`.
   It does not preserve the provider response body message in that exception.
3. `executeCopilotTurn()` recognizes `provider-http-error`, copies numeric
   `status` to `providerStatus`, and constructs the generic message shown in
   the report. Since 401 is not in the transient-status list, no retry is
   performed.
4. The CopilotKit route passes the failure code and retry/billing metadata to
   `CopilotKitAgentError`, but does not pass `providerStatus`. The agent's
   `RUN_ERROR` metadata likewise contains no provider status.
5. The chat surface replaces the event text with its own safe failure message
   and only retains retry/billing flags plus an optional validation issue.
   Therefore the status is available in the executor outcome and ledger, but
   is not visible in the CopilotKit event metadata or rendered chat failure.

The quoted application message,
“Copilot provider rejected the request. The user message is retained; retry
only after reviewing the provider status.”, is generated by
`executeCopilotTurn()` for this non-ambiguous provider rejection. It is not the
raw Azure message. The raw Azure message was captured by the direct terminal
request above; the application client discards that response-body detail.

## Cause assessment

- **Invalid key:** possible. Azure explicitly lists an invalid subscription key
  as one cause; key presence does not prove validity or subscription status.
- **Endpoint/key resource mismatch:** possible. Azure explicitly lists a
  wrong API endpoint as the other cause. The endpoint format passes local
  validation and resolves to an HTTPS Azure OpenAI host, but local evidence
  cannot verify that the key belongs to that resource.
- **Deployment missing:** not indicated by the 401 response and not
  independently verified. The deployment name is present in the request.
- **Local provider configuration error:** not supported by this evidence.
  The terminal request passed local required-setting checks and reached Azure,
  which returned an authorization response.
- **Other provider rejection:** no evidence of a separate cause. The best
  supported classification is **Azure rejected the configured key/resource
  endpoint pairing**. The available evidence cannot determine whether the key
  itself is invalid or the endpoint is mismatched.

No Azure configuration value or credential was changed. Verify in Azure that
the configured key is active and belongs to the configured resource endpoint;
also verify that `gpt-4o-mini` exists in that resource before making another
request.
